# PixelPin architecture

PixelPin uses a .NET 8 WPF process with a small native interop boundary.

## Capture

- Services/ScreenCaptureService captures each physical display independently before its overlay is displayed, avoiding allocation for gaps in a non-contiguous virtual desktop.
- Services/ScreenCaptureService.EnumerateZOrderWindows walks the desktop with EnumWindows, which returns windows top-most first, and filters out shell surfaces (Progman, WorkerW, Shell_TrayWnd), cloaked UWP hosts (DwmGetWindowAttribute / DWMWA_CLOAKED), tool/no-activate/transparent windows, untitled windows, and PixelPin's own process. The overlay therefore highlights only windows the user can actually capture.
- Windows/SelectionOverlayWindow is instantiated once per Screen. Each overlay owns only that monitor's image; final crops are copied into detached pixel buffers so stickers and history actions do not retain the full screen source.
- Windows/SelectionOverlayWindow converts the z-order window list into its own device-independent space once per size change, then uses it for both pointer hover highlighting and drag snapping. A click on a highlighted window crops from the descriptor's physical bounds rather than the scaled overlay rectangle, so the exported image is exactly the window rectangle.
- Windows/SelectionOverlayWindow exposes IsRenderReady, set on the first layout pass that applies the dimmer. Rendering the overlay before that pass yields an undimmed surface, so the desktop probe waits on this flag rather than sleeping a fixed interval.
- Services/WindowCaptureService.CaptureWindowHandle is the single entry point for a window capture. Utilities/WindowCapturePlanner decides the route order from four facts (visible fraction, graphics-capture availability, whether the window is fully on screen, whether it is minimised) and is a pure function, so the ordering rules are unit tested without a desktop. The rule is that a window the user can fully see comes from the screen, and anything else starts with a route that does not depend on what is stacked on top.
- Services/WgcCaptureService captures a window through Windows.Graphics.Capture, reading the window's own composed surface. It owns one lazily created D3D11 device (hardware, falling back to WARP for remote sessions), rebuilds it after a lost device, and copies each frame into a staging texture before reading it back row by row because RowPitch exceeds the row width. Frames are premultiplied BGRA, which is exactly PixelFormats.Pbgra32, so the window's real alpha is preserved and rounded corners stay rounded.
- The capture border is suppressed through GraphicsCaptureSession.IsBorderRequired, which needs the 22621 projection. The project therefore targets net8.0-windows10.0.22621.0 with SupportedOSPlatformVersion at 10.0.19041.0, so the build sees the newer API while the runtime requirement does not move; every newer call is guarded.
- Services/WindowCaptureService also renders a single window with PrintWindow and PW_RENDERFULLCONTENT, which asks the window to draw its own content instead of returning whatever covers it. This is the fallback when graphics capture is unavailable, and it is cheaper, but a window that renders through DirectComposition can silently return black.
- Window capture is inspected before it is accepted. Utilities/CaptureQuality is a pure function of pixel data, so the decision is unit tested rather than tuned against a live desktop. It rejects transparent, all-black, and wrongly sized images. A flat single-colour image is ambiguous, so it is only rejected when PrintWindow itself also reported failure; that keeps a genuinely blank window capturable while still refusing an unrendered one.
- Every route is tried in plan order and each refusal is collected, so a total failure reports which routes were attempted and why each was refused. A screen crop is only offered when the window is at least half visible, because below that it returns more of another window than of the target.
- GDI does not maintain the alpha channel, so a rendered window arrives fully transparent and would display as blank. WindowCaptureService sets every alpha byte to opaque before converting to a WPF bitmap. The graphics-capture route skips this deliberately, because its alpha is real.
- Window bounds come from the DWM extended frame bounds rather than GetWindowRect, which includes the invisible resize border and would otherwise add a transparent margin to every capture.

## Scrolling capture

- Utilities/ScrollStitcher owns the entire decision about whether two frames are consecutive: it measures the vertical offset from the pixels and refuses when the pixels cannot prove one. It is pure arithmetic over buffers, so the interesting cases - repeating content, uniform content, a scroll larger than the viewport - are unit tested without a desktop or a target application.
- The offset is never derived from the wheel delta. A wheel notch scrolls a different distance in every application, and under smooth scrolling the same notch lands on a different offset each time, so the only reliable source is the frames themselves.
- The step size is adaptive for the same reason. The first step sends one notch, the resulting offset is divided by the notches sent to learn the application's own distance, and later steps are widened towards a third of the region. The widening is bounded and is treated strictly as a speed optimisation: if a widened step cannot be measured, the step is halved and retried, and the capture only stops when even a single notch cannot be verified. A faster capture is worth nothing if it turns a working one into a refusal.
- Wheel notches are sent as separate events, one per notch, with a short gap. WPF's ScrollViewer reads only the sign of the delta and scrolls a fixed three lines, so a single event carrying three notches scrolls exactly as far as one notch - a failure that is invisible unless the measured offsets are inspected.
- Settling time grows with the number of notches, because applications animate each one. A wide step read too early returns a frame that is still moving, which matches no offset at all and is indistinguishable from changed content unless the delay is scaled with the step.
- Scoring uses two measures because one is not enough. The fraction of pixels that agree within tolerance rejects offsets that are simply wrong, but on smooth content neighbouring offsets all agree, so the fraction is 1.0 across a range of them. The mean per-channel difference, with each pixel capped, is what makes the winner unique. The cap keeps a region that legitimately never matches - the moving scrollbar - from dominating the average.
- The match fraction is a gate, not a verdict, and the gate is deliberately loose. A real screen region almost always contains something that does not scroll with the content: a scrollbar whose thumb moves, a fixed header, a focus ring. Content that scrolls perfectly rigidly therefore scores around 0.95 rather than 1.00. A gate at 0.95 rejects exactly the regions users select, so it sits at 0.85 and the mean difference does the discrimination. This was a real defect, not a precaution: a rigid 216 pixel scroll measured 0.948 and was refused.
- Early pruning must not destroy the evidence it prunes. The scoring loop abandons a candidate as soon as it cannot reach the required fraction, which is what keeps the search affordable, but it reports a fraction of zero for that candidate. Reusing those numbers to explain a failure reports "nothing matched" when the truth was "0.948 against a gate of 0.95", so the failure path re-scores without pruning before it says anything.
- Ambiguity is a first class outcome, not a tie-break. Content that repeats matches at two distant offsets, and picking the higher scoring one produces a long image with content silently duplicated. ScrollStitcher reports Ambiguous and the capture stops.
- Services/ScrollCaptureService injects wheel events with SendInput rather than posting WM_MOUSEWHEEL, because many applications ignore the posted message. The cursor is moved into the region first, since the system routes a wheel event to whatever is under the pointer, and restored afterwards.
- The capture reads frames after a settle delay and retries, because applications animate their scroll: the first frame after a wheel event can be mid-flight and match nothing.
- The service runs off the dispatcher. It sleeps between wheel events, and blocking the dispatcher would stall the very application it is waiting for, so the capture is started on a worker and the result is marshalled back.
- A partial result is returned with the reason it stopped. Rows already stitched are real content, so they are kept, but the reason travels with them because a stitched image that stopped early looks exactly like a complete one.

## Interaction geometry

- Utilities/SelectionGeometry, Utilities/SelectionSnap, Utilities/SelectionKeyboard, Utilities/WindowHitTesting, Utilities/StickerGeometry, and Utilities/StickerAlignment hold the pure geometry and are free of window types. They are covered by the console tests, which is why snapping, keyboard nudging, alignment, z-order hit testing, and aspect-ratio resizing can be verified without a desktop session.
- Windows/SelectionOverlayWindow reuses a fixed-size writable magnifier bitmap and pixel buffers while the pointer moves, avoiding per-event BitmapSource allocation.
- Windows/SelectionOverlayWindow routes arrow keys through SelectionKeyboard, which owns both the step sizes (1 pixel, 10 with Ctrl) and the mapping from arrow to edge. The overlay's key handler and the desktop probe call the same method, so the probe cannot drift from the shipped path. A keyboard adjustment also clears the remembered exact window crop, because a hand-placed selection is no longer the window rectangle.

## Presentation

- Themes/Tokens.Light.xaml holds every colour, corner radius and font used by the interface. A window that writes a literal `#F4F6F8` is a bug: the literal cannot follow a theme, and the value ends up duplicated across files with no way to tell which copy is authoritative.
- Themes/Controls.xaml carries hand-written templates for button, text box, combo box, check box, slider, scroll bar, list box, tab control and tool tip. WPF on .NET 8 has no built-in Fluent theme (that arrived in .NET 9), and the portable build ships without third-party UI libraries, so the templates are local. They honour the control's own Background/BorderBrush/Foreground through TemplateBinding, which keeps per-window tints possible.
- Themes/Icons.xaml draws icons as 16x16 geometry rather than glyphs. Segoe MDL2 and Segoe Fluent Icons do not share every codepoint, and a missing glyph renders as a box; a Path cannot miss.
- App.xaml merges tokens before controls, then sets the Window-level defaults (font, foreground, background, layout rounding). The order matters: the control templates resolve their token lookups while being parsed.
- Themes/Tokens.Light.xaml and Themes/Tokens.Dark.xaml declare the same key set, and every window references them through DynamicResource. That pairing is what makes a runtime theme switch a dictionary swap instead of a restart. A missing key does not fail the build - it resolves to nothing and the control renders invisible - so the render harness compares the two key sets by name and re-renders every window in both themes.
- Services/ThemeService owns the swap. It replaces the first merged dictionary whose source ends in Tokens.*.xaml, follows the OS through SystemEvents.UserPreferenceChanged plus the AppsUseLightTheme registry value when the preference is System, and paints the non-client area through DWM (immersive dark mode, rounded corners, border/caption/text colours). WPF cannot draw the title bar, so a theme that only changes window content leaves a white strip above a dark window.
- The two dictionaries are not a palette inversion. An accent fill has to get lighter in dark mode to keep white label text above 4.5:1, and AccentTextBrush exists separately from the accent fill because text on a tinted surface and a fill under white text have opposite contrast requirements. Hover and pressed states are translucent overlays (black on light, white on dark) so one template serves neutral and saturated buttons alike.
- The capture overlay and the sticker keep their own dark chrome in both themes. They float over arbitrary desktop content, so their legibility cannot depend on what the user's app theme happens to be; the render harness exempts them from the dark-render comparison for that reason.
- Every interactive control carries a FocusVisualStyle, except the text field, which signals focus with a 2px accent edge like Fluent. The templates are hand-written, so a focus ring is opt-in per style and a missing one is invisible in a screenshot while leaving the window unusable from the keyboard.
- Motion is limited to a 120ms fade (and a 6px rise for the capture bar) when a floating toolbar appears, plus a 100ms fade for tool tips. There is no looping animation and nothing animates on every frame of a drag.
- The capture dimmer (`#A6000000`) and the beautifier presets are deliberately outside this layer. The desktop probe asserts specific composite ratios and exported pixels for them, so they are behaviour, not decoration.

## Editing

- Windows/ImageEditorWindow separates the annotation layer from the source bitmap and stores operations, not image copies, in its undo stack.
- Utilities/ImageProcessing pixelates and box-blurs regions into detached bitmaps. Mosaic and blur are committed as bitmap overlays instead of live XAML effects, so the exported PNG matches the preview pixel for pixel; the desktop probe asserts this by comparing colour counts before and after.
- Utilities/ImageBeautifier splits into ComputeLayout and Beautify. The layout is pure arithmetic and unit tested; the drawing step needs a WPF render context and is probe tested. The layout also decides the effective shadow size, because the shadow has to fit inside the padding, and the renderer reads those values back from the layout so the preview and the export cannot disagree.
- Windows/BeautifyWindow previews with the same renderer the export uses, downscaling the source for display only. Export always runs at full resolution.

## Stickers

- Windows/StickyWindow is independent of the settings window. Closing settings therefore leaves active stickers and registered hotkeys intact.
- Sticker rotation is a LayoutTransform rather than a RenderTransform. A render transform would rotate the image inside an unchanged box and stretch it once the window dimensions were swapped; the layout transform re-measures the image inside the new box so proportions are preserved.
- Sticker sizing goes through Utilities/StickerGeometry so the aspect-ratio rule, the minimum size, and the rotated-ratio swap are all testable without a window.
- Sticker dragging runs a custom mouse-capture loop rather than WPF's DragMove. DragMove is a modal loop that reports nothing until it ends, and alignment needs a position update on every mouse move. Pointer tracking converts the physical screen point back into the device-independent virtual-desktop space that Window.Left and Window.Top use, so the grabbed point stays under the cursor at any DPI scale.
- The mouse capture belongs to the same element that carries the move and release handlers (the frame Border), never to the window. WPF delivers mouse input only to the capturing element, so capturing the window left every handler on the frame unreachable: the sticker did not move and never left its dragging state. Both must stay on one element.
- Alignment itself is Utilities/StickerAlignment, a function of rectangles only. Windows/StickyWindow asks AppController for the other stickers' bounds through a delegate, so the sticker never needs to know the registry exists.
- Alignment pairs like with like: edges snap to edges and centres to centres. Matching every position against every line let a sticker's centre snap onto the screen's edge, which pushed half the sticker off the screen on what the user intended as a small placement.
- Every drag result passes through StickerAlignment.ClampToDesktop, which keeps at least 48 DIP of each axis inside the desktop. A sticker dragged entirely past an edge can never be grabbed again, and the drag stops being useful exactly when the user is least likely to notice.
- Drag diagnostics go through an optional Trace callback that AppController points at the application log. Only observable changes are recorded - drag start, a guide appearing or moving, drag end with its displacement and sample count - because a line per mouse move would write hundreds of entries per drag and push the useful ones out of the rotating log. A drag that reports zero samples is the signature of input that never reached the window.
- Windows/AlignmentGuideWindow draws the guides on a click-through sheet covering the virtual desktop, carrying WS_EX_TRANSPARENT and WS_EX_NOACTIVATE so it cannot steal input or focus from the drag that owns the mouse capture. A sticker closes its guide window with itself, so no hidden window is left behind.
- Windows/StickerManagerWindow coordinates active independent sticker windows through explicit group, layer, mouse-through, and batch-close commands without making a manager window their owner.

## Services and persistence

- Services/OcrService wraps the Windows OCR engine. The platform type is only reachable because the project targets `net8.0-windows10.0.19041.0`, which brings in the Windows Runtime projection. The recognizer needs an installed language pack, so every entry point reports whether it can run and why it cannot, instead of returning an empty result that looks like a successful recognition of an image with no text.
- Utilities/OcrText holds the text shaping and is free of Windows Runtime types, so it is unit tested without a language pack. The recognizer returns one word per Chinese character and joins them with spaces in OcrLine.Text, so copying that text verbatim would produce `截 图 贴 图`. The words are reassembled instead, and the space decision is made per adjacent pair: two Chinese characters never take a space, and a script boundary is left as the recognizer found it. A per-line rule cannot express that, because `截图 tool` needs opposite answers at its two boundaries.
- Windows/OcrWindow keeps the recognised text editable. Recognition of a small or low-contrast capture can misread a character, and the user is the only one who knows what it should say.
- Services/HotKeyService owns a hidden native message window for RegisterHotKey and a low-level keyboard-hook fallback for applications that consume ordinary shortcut messages. It matches only configured shortcuts, suppresses duplicate delivery, and does not persist keyboard input. Six features register through it: region capture, region capture with pin, full screen capture, paste as sticker, mouse-through toggle, and close-all-stickers.
- Models/HotKeyDefinition owns both directions of the shortcut text format. The settings page records a combination through TryCreate and renders it through the same FriendlyKeyName table the parser accepts, so anything the recorder produces can be read back. The parser handles digits and punctuation explicitly, because Enum.TryParse reads a bare numeric string as the enum's underlying value: "1" would otherwise resolve to Key.Cancel and silently change a saved shortcut.
- Services/SettingsService persists Services/AppSettings, whose Normalize method restores defaults for missing fields so a settings file written by an older version still loads. Computed members such as the shortcut table are marked JsonIgnore so they never leak into the file.
- Services/HistoryService saves PNGs and a JSON index in %LocalAppData%\PixelPin; bounded entry and disk limits remove old items, while history and imported file images bypass the WPF URI image cache.
- Services/ApplicationLogService retains a small local rolling diagnostics file. Its write path is isolated so a full disk cannot break capture, and it never receives image data.
- Services/EnvironmentWatchService listens for the three desktop notifications a tray application cannot assume away: display-settings changes, resume from sleep, and session unlock or remote reconnect. SystemEvents raises them on its own thread, so every callback is marshalled onto the dispatcher before it reaches a handler; window and hotkey APIs have thread affinity.
- Recovery is coalesced. A resolution change arrives once per monitor and a dock or undock delivers a display change and a resume within the same second, and each pass tears the hotkeys down and registers them again, which is a moment where a keypress can be lost. AppController therefore waits 400 ms of quiet before acting.
- Hotkeys are cleared before they are re-registered. RegisterHotKey returns ERROR_HOTKEY_ALREADY_REGISTERED for an id that is still live, so a plain re-register would report a bogus conflict and leave the user with no shortcuts at all - the exact failure the recovery exists to prevent.
- Sticker recovery is Utilities/StickerGeometry.ClampIntoDesktop, a function of two rectangles. It leaves a sticker that is still partly reachable alone, because a deliberate overhang is a layout choice rather than a bug, and only pulls back one with no usable visible area. It works in DIPs against SystemParameters.VirtualScreen*, not SystemInformation.VirtualScreen, which reports physical pixels and would be wrong above 100% scaling.
- Topmost is re-asserted without activation. Assigning the same Topmost value is a no-op, so StickyWindow.ReassertTopmost drops the style and reapplies it; calling Activate would steal focus from whatever the user came back to.

## Testing boundary

- The console test project is granted InternalsVisibleTo so it can drive the editor's, sticker's, and overlay's real input handlers (BeginDraw/EndDraw, Rotate, ApplyKeyAdjustment, DragToForTesting) instead of a parallel test-only code path. The handlers delegate to those methods, so the tests exercise the shipped behaviour.
- Handlers attached in XAML can run while InitializeComponent is still building the tree, before fields declared later in the XAML exist. The editor's colour and font-size pickers therefore read their own event source instead of the backing field, and ApplyStroke tolerates a null DrawingCanvas. The desktop probe opens every tool window specifically to catch this class of fault.
- The probe raises genuine routed events for the shortcut recorder rather than calling the handler directly, so the XAML EventSetter wiring and the read-only field state are both covered.
- tests/PixelPin.Tests/DesktopProbe.cs is an opt-in probe that requires an interactive desktop. It verifies screen capture dimensions, z-order enumeration, overlay construction and dimming, real cursor hover highlighting, keyboard nudging, editor annotation and redaction output, sticker rotation proportions, sticker alignment and its guides, beautified export pixels, the shortcut recorder, OCR round-tripping rendered text, window rendering and its quality gate, and that every tool window loads with the real application resources.
- The occlusion claim is proven by construction rather than inferred: the probe places two known-coloured windows exactly on top of each other and asserts that a screen capture of that rectangle returns the upper window's colour while every window route returns the lower window's own. It repeats both routes through the overlay's own selection path, so the wiring between the route decision and the completed capture is covered and not only the service underneath it. The graphics-capture route is additionally checked for Pbgra32 output and for capture-border pixels, and the whole chain is re-run with graphics capture declared unavailable to prove it degrades to the GDI render instead of failing.
- The scrolling claim is proven by decoding the result. The probe's scrollable content gives every row a unique colour, so the stitched image can be turned back into the sequence of source rows it contains. The assertion is that the sequence advances by exactly one per row, which fails on a duplicated row, a missing row, and a stitch built on the wrong offset alike; "the image got taller" would pass on all three. The same window type is then filled with repeating content and the probe asserts the capture refuses: one frame, unchanged height, and a stated reason.
- The probe's scrollable window had to be verified before the stitcher could be blamed for anything. Its content is declared at the window's own DPI so one source row maps to one physical pixel, and the probe decodes the first frame's rows to confirm that mapping holds before it runs the capture. Two probe-side faults were found this way and neither was a product defect: a ScrollViewer centres content that is narrower than its viewport, and a row index encoded in a single byte aliases every 256 rows - at which point offsets 255 apart genuinely fit equally well and the stitcher was right to refuse.
- The probe substitutes the packaged window icon with an in-memory one. App.xaml's icon URI is assembly-qualified, but the probe's entry assembly is the test host, so the pending icon decode would otherwise fail on the dispatcher and abort the probe with an error unrelated to any product logic. The real icon is covered by the app smoke test, which creates the real overlay window.
- The UI redesign is verified by a render harness rather than by the probe, because the probe needs a mouse and write access outside the workspace. The harness hosts the real Application resources, renders every tool window off screen at 96 and 192 DPI, dumps each visible TextBlock with its slot, and asserts the things a screenshot cannot: slider wiring in both directions, checkbox marks, contrast ratios per theme, tool-button state, toolbar bounds against the screen, the DWM chrome values, tab order, focus-ring coverage, and that no window overflows its own minimum size at 150% scaling.
- Two harness findings were product bugs and one was its own: the capture bar really did hang off the screen on the first selection, the settings window really did keep a previewed theme after Cancel, and the "no dark difference" result was the harness rendering under a controller that had already applied the desktop's own theme.
- The probe and the unit checks write through PIXELPIN_DATA_DIR, which the test entry point points at the temp directory. Before that, a probe run wrote into the real %LocalAppData%\PixelPin and failed with an access denial on a machine that restricts it - a test that damages the profile it is testing is not a test.
- The probe always contributes one window of its own to the window-rendering check, painted with a gradient. A desktop running only hardware-accelerated applications has nothing PrintWindow can capture, and the check read that as "the render route is broken". A skip that depends on what the user happened to have open is not a signal.
- A session that is not permitted to open a Windows.Graphics.Capture session reports E_ACCESSDENIED. The probe treats that specific code as a skip with a stated reason rather than a failure, because it describes the machine; every other failure still fails, so a real breakage cannot hide behind it.

The architecture deliberately keeps image capture, UI, and persistence separate. Window capture now has three interchangeable routes behind one entry point, and the ordering that chooses between them is a pure function that the console tests cover. Hardware-accelerated, HDR, and partly off-screen windows are captured through their own composed surface; a window that no route can reach is reported with each route's reason rather than captured as a black image.
